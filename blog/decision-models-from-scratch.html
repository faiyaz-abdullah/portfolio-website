Decision Models from Scratch: How Jev-Style AI Picks Instead of Writes

1. Writing versus picking

Imagine a shop that gets 50,000 customer emails a day. A program must send each email to the right team: billing, shipping or tech support. It must also flag urgent ones.

Many programs today ask a chat AI (a large language model, or LLM) to do this. The LLM answers with a sentence:

"This email should go to the shipping team because the customer says the parcel has not arrived…"

But the program only needs one word: shipping. It must now dig that word out of the sentence and hope the LLM didn't write "Shipping" or "the delivery team". This is slow, costs money, and sometimes breaks.

A decision model works differently:

Chat LLMDecision model
How it answersWrites text, one token at a timePicks one option from a list you give it
What you get backA sentence you must parseA typed answer plus a probability, e.g. shipping, 86%
SpeedSlow (each word is a new step)Fast (one pass)
Can it break the format?YesNo: it always returns one of your options

The core idea: an LLM answers by writing. A decision model answers by picking. You give it a question and a fixed list of allowed answers. It picks one and tells you how sure it is.

2. System 1 and System 2

The psychologist Daniel Kahneman described two ways people think:

  • System 1 is fast and automatic. You see a face and instantly know the person is angry.
  • System 2 is slow and careful. You work out 17 × 24 step by step.

Reasoning LLMs that "think out loud" are System 2. Decision models are System 1: fast, bounded judgments.

AI agents make hundreds of small System 1 choices. Which tool next? Is this result relevant? Did that step fail? Should a human check this? None of these needs a paragraph. Each needs one choice and a confidence number.

3. Meet Jev

Jev is the model that made this idea popular. It comes from TypeSafe AI, a San Francisco start-up founded by Diogo Almeida, a former OpenAI researcher. It was released in early access on 15 September 2026, and TypeSafe calls it the first public "System One model".

InputA state (the facts, e.g. an email) plus one or more typed questions
OutputTyped decisions with probabilities and confidence. No text.
Price$0.042 per million input tokens. Output is free.
Speed (company claim)70–500 ms end to end
Context64k tokens per request (version jev-1.13.0)
Training methodRLCD: Reinforcement Learning for Calibrated Decisions
Not publishedArchitecture, model size, base model, exact training recipe

The three question types

TypeQuestion shapeWhat comes backGood for
Choice"Pick one of these K options."The chosen option, a probability for every option, and a confidence valueRouting, picking a tool
Score"Rate this on a scale you define (e.g. 1–5)."A level, a probability for each level, and a confidence valueUrgency, quality, risk
Noul"Is this statement true?"The probability of "yes"Yes/no gates

You can ask several questions about the same state. Jev answers them independently and in parallel, so you only pay for the state once.

What the money looks like

Take 1,000,000 decisions with 500 input tokens each. That is 500 million tokens.

  • Jev: 500 × $0.042 = about $21. Output is free.
  • A typical LLM: input costs $0.20–$10 per million tokens. That is $100 to $5,000, before paying for the words it writes.
⚠️

A fair warning: TypeSafe's biggest speed and cost numbers come from its own tests. Always measure on your own data.

4. How a decision model is built: the pipeline

Every decision model goes through the same big pipeline:

  1. Raw text→
  2. Pretraining→
  3. Post-training→
  4. Decision readout→
  5. Decision data & training→
  6. Calibration→
  7. Serving→
  8. Your app

Pretraining. The model plays one game trillions of times: guess the next token. To get good at this, it must learn grammar, facts and common sense. This knowledge is the "brain" every decision model relies on.

Post-training. The model learns to behave well. Common methods:

  • SFT (supervised fine-tuning): learn from good examples.
  • RLHF: learn from human preferences.
  • RLVR: learn from right/wrong checks.

Decision readout. The model is turned from a writer into a picker (see Section 5).

Decision training and calibration. The model is trained so that its probabilities are honest (see Section 6).

What is known and what is not: TypeSafe has not shared Jev's architecture or training recipe. What we can study is the open, Jev-style models that many people have built since launch, plus the research on them. 5. Turning an LLM into a picker

How do you make a language model pick instead of write? Open projects use five designs:

DesignHow it worksWeakness
Classifier headA fixed output layer, one slot per labelNew labels mean retraining
Per-option yes/noAsk "Is option k right?" once per optionSlow, and options are never compared
Letter logitsList options as A, B, C… and read the model's score for each letterOnly about 26 options
Suffix scoringNumber the options [1], [2]… and score each answer k]Option order can bias it (fix: shuffle when training)
Pointer headA new layer matches a question vector to each option vectorMust be trained for every new base model

The suffix-scoring trick, simply

  1. Write the options as [1] billing, [2] shipping, [3] tech.
  2. Start the model's answer with Best answer: [.
  3. For each option, measure how likely the model is to continue with 1], 2], 3]…
  4. Turn those scores into probabilities with softmax:
P(option k) = e^(score_k) / sum of e^(score_j) over all options

The closing bracket matters. 1] can never be the start of 12], so the options never get confused, however many there are.

The model reads the long input once and then scores all short answers in parallel. Even 150 options need only one read plus a few tiny steps. There is no word-by-word writing at all.

A worked example. Suppose the scores for billing, shipping and tech give these values of e^score: 2.718, 7.389 and 1.105. Their total is 11.212. So:

Optionbillingshippingtech
Probability0.240.660.10

6. Honest confidence: the idea behind RLCD

Your software will act on the model's confidence, for example: "if confidence is below 0.8, ask a human." So the confidence must be calibrated. When the model says "70% sure", it should be right about 70% of the time.

Common training methods can damage this:

  • RLHF rewards answers that sound good, which can teach a model to sound confident.
  • Right/wrong rewards push the model to put everything on its top guess, i.e. to say 100%.

The fix is a proper scoring rule: a reward that is highest, on average, when you report your true belief. One example is the Brier score, a penalty equal to (probability − outcome)².

Suppose a type of email is truly urgent 70% of the time. Compare the average penalty (lower is better) for different confidence levels:

Reported confidence50%70%90%100%
Average Brier penalty0.2500.2100.2500.300

The honest answer wins. Saying "100% sure" is the worst choice.

TypeSafe's RLCD is reinforcement learning aimed at calibrated decisions. Its exact recipe is private. Proper scoring rules are the standard idea that makes "rewarding honesty" possible.

7. Lessons from open research

An October 2026 research paper, LLM-as-Jev, studied in detail how to build Jev-style models from open LLMs. Its key findings are useful for anyone building or using decision models.

1

A good LLM is already a decision model. A small open model (Qwen3.5-4B) with suffix scoring and no training at all scored 81.4% on the public JevBench benchmark. That is on par with several fine-tuned community models. Its probabilities were already well calibrated.

2

Fine-tuning helps small models and narrow tasks most.

ModelTaskBeforeAfter fine-tuning
0.6B modelBanking77 (77 intents)22.2%60.5%
4B modelBanking7769.0%75.4%
4B modelJevBench (broad)81.4%84.0% (with LoRA)

Fine-tuning teaches format and discrimination. It does not add world knowledge the model never had.

3

Data balance matters more than data size. Two traps:

  • The intent trap. Training only on intent-routing data, with no yes/no questions, made the model say "yes" too often. It also avoided "none of these" and became over-confident. Overall accuracy dropped from 81.4% to 74.9%.
  • The short-context trap. Training only on short examples made long documents worse. Adding a few thousand long examples fixed it.
4

Protect the model while training. Without a safeguard, fine-tuned models started adding junk text after their answers. The fix is a KL anchor: a penalty that keeps the new model close to the original. Accuracy scores alone did not reveal this damage.

5

A thinking budget closes the gap. Letting the same small model "think" for up to 4,096 tokens before answering raised its accuracy to 94.8%. That is on par with a frontier model, at an estimated 5.5× lower cost. This "Thinking Jev" setup is like a dial between System 1 and System 2.

8. Using a decision model well

Put each kind of work in the right layer:

LayerGood atNever give it
Plain codeMath, dates, limits, permissions, paymentsFuzzy meaning
Decision modelBounded choices, scores, yes/no judgmentsWriting, exact math, final authority
LLMWriting, explaining, open reasoningUnsupervised power over important actions

Good habits:

  • Ask atomic questions. Not "Is this trade safe?" but several small, clear questions, combined in code.
  • Always add an escape option such as "other" or "human review".
  • Keep thresholds in your code, and tune them on your own data.
  • Pin the model version so your thresholds stay valid.
  • Start in shadow mode. Run the model next to your current system, compare, and switch on step by step.

Known weak spots: arithmetic, counting, comparing dates, multi-step logic, distraction by irrelevant text, and manipulation hidden inside user-written input.

💡

Typed is not the same as correct. A decision model can never return a malformed answer. But it can still pick the wrong option.
